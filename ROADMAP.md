# Zoxide Doctor Roadmap

## Current Status

v0.2.0 is tagged and published (release archives + SHA256SUMS via GitHub Actions, generated Homebrew formula). Remaining work: Homebrew tap plus the upstream to-dos below.

Locked decisions:

- Primary workflow: `z <query>` first, then no-arg `zdr` if zoxide lands in the wrong directory.
- Repeated no-arg `zdr` calls are the rejection/escalation signal.
- `zdr <query>` is an experimental direct lookup, not the default zoxide replacement path.
- Recovery context comes from recorded shell state, not shell history scraping.
- Correction memory is zdr-owned state, not zoxide frecency boosting.
- Runtime target: TypeScript on Bun, distributed as a Bun-compiled executable.
- Provider layer: Pi provider/model SDK (`@earendil-works/pi-ai`); completion/model APIs only — no Pi agent loop, harness, TUI, tool execution, or session machinery.
- Default provider: `openai-codex` / `gpt-5.6-terra` at minimal reasoning effort, authenticated via ChatGPT-plan OAuth (`zdr provider-login openai-codex`). Env-key providers (e.g. `OPENROUTER_API_KEY`) are the documented alternative.
- Cold start: 150ms local budget (`scripts/timing-baseline.ts`); provider SDK imports stay dynamic.

## Shipped

### v0.1.0 — Core Recovery Loop

Shell wrappers for zsh, bash, and fish record `z` attempts; no-arg `zdr` repairs the last bad jump from zoxide candidates with a bounded, redacted prompt and a strict JSON `candidate_id` response. Second attempt escalates, third opens an `fd` + `fzf` picker. `zdr <query>` direct lookup with `corrections.json` memory (cache-first, stale-path eviction). Local telemetry (tokens, cost, prompt-cache fields where exposed) with `zdr debug-events` / `zdr prune-events`, timing diagnostics, v1 config file, install docs.

### v0.2.0 — Providers, Escalation Tier, Evals

- `openai-codex` / `gpt-5.6-terra` default via ChatGPT-plan OAuth; measured 96% eval accuracy, 100% stability across 3x50 repeats, p50 ~1.4s.
- Optional escalation tier for the second no-arg `zdr` (`zdr config-escalation <backend> <model>`, recommended `claude sonnet`); Claude backend runs on `@anthropic-ai/claude-agent-sdk` using the local `claude` login.
- Read-only import of Pi CLI OAuth logins (`~/.pi/agent/auth.json`) into zdr's own store.
- `zdr provider-discover`: token-free per-backend readiness report with tier summary.
- Alias memory: recovery-mode picker selections and high-confidence repairs stored in `corrections.json` and injected as the top candidate on later attempts.
- Eval suite (`src/eval/`, 50 cases, 10 categories): offline recall via `bun scripts/run-evals.ts`, spend-gated live runs, telemetry-to-case mining.
- Codex client-identity shim (`src/provider/codex-identity.ts`) so `gpt-5.6-luna` routes correctly.
- Release automation: archives, SHA256SUMS, Homebrew formula generated by `bun run release:prepare`.

## Backlog

Open ideas, not scheduled. Former tracker keys in parentheses are history only.

1. **`zdr stats` and recovery observability** (AUR-422). One command that summarizes recent telemetry: escalation rate, 1st/2nd/picker attempt distribution, correction-cache hit rate, provider latency percentiles, and cost over a window. Add flag-gated, leveled logging of the recovery path (context → candidates → prompt → provider → selection → cd) and a countable taxonomy of failure/fallback events (no recorded `z`, no candidates, provider error, picker fallback). Any export hook is strictly opt-in. Acceptance: one command summarizes behavior; each failure/fallback mode is countable; nothing leaves the machine unless opted in.
2. **Richer recovery test scenarios** (AUR-423). Deterministic unit or e2e tests (not only live evals) for: ambiguous queries (`dev` matching several repos); escalation (2nd no-arg `zdr` excludes the prior wrong pick, 3rd opens `fzf` seeded with the original query); direct lookup cache hit vs. cold miss → model → cache write, plus stale-path eviction; empty zoxide DB and no recorded `z` → safe failure; `fd` scan candidates; redacted display paths in the prompt; deep vs. shallow matches, case-insensitivity, partial tokens. Reuse the eval fixtures rather than duplicating them.
3. **Self-contained end-to-end tests** (AUR-424). A hermetic harness that drives the real CLI against checked-in fixtures: fake zoxide DB, temp directory tree, recorded `last_z.json`, `corrections.json`; `$HOME`/config/state isolated through env overrides; provider stubbed so it runs offline with no key (one optional live lane behind a flag); `fzf` picker faked or given a non-interactive selection. Acceptance: the e2e lane passes on a clean machine with no zoxide DB, config, or provider key, and never touches the real home.
4. **Cache tuning** (AUR-425). Measure correction-cache hit rate and justify the stale-path eviction policy from data; consider normalized/near-miss query matching; memoize candidate gathering (zoxide query + `fd` scan) within one escalation session. For provider prompt caching, keep the stable prefix (instructions, format rules) first and volatile candidates last; [provider-recommendations.md](docs/provider-recommendations.md) already shows realistic prompts sit below the ~1024-token prefix-cache threshold, so revisit only if prompts grow.
5. **Codex app-server provider** (AUR-426). A backend behind `src/provider/` that drives the local `codex` app-server over JSON-RPC stdio (`initialize` → `thread/start` → `turn/start`) to get a strict JSON `candidate_id`, reusing an existing `codex login`. Use an isolated temporary `CODEX_HOME` (link or copy `auth.json`, minimal `config.toml`) and never modify the user's real Codex home. Map usage and latency into `src/provider/usage.ts` and telemetry; expose it as a selectable provider in the v1 config. Completion/selection only: no Codex agent loop, tools, sandbox, approvals, or session machinery. Acceptance: with a valid `codex login` and no provider API key, `zdr` selects a candidate through this backend and the rest of the recovery path is unchanged.
